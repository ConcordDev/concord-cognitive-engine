# Live QA walkthrough — all 266 lenses (concord-os.org)

Systematic pass through every lens directory in `concord-frontend/app/lenses/`,
authenticated as fresh test account `qatestrunner01`, against production
(commit `a0828eb59`, PR #933). Goal: a complete map of what's broken so the
fix pass isn't whack-a-mole.

**Method:** navigate to `/lenses/<name>`, screenshot, flag anything visually
broken (blank/black viewport, error boundary, stuck skeleton loaders, raw
JSON dump, obviously-undesigned generic scaffold). Console/network deep-dive
reserved for lenses that look suspicious on the visual pass — full detail
pulled for those, not for every lens (266x full console dumps isn't a good
budget trade). Clean-looking lenses are logged as OK with no further detail.

Cross-cutting issues already confirmed platform-wide (not re-logged per lens):
- **Rapid client-side navigation artifact**: navigating between two lenses back-to-back
  (as fast as this automated walk does it) can leave the page showing the PREVIOUS
  lens's content/title after the URL has already changed. Confirmed once (agriculture),
  self-resolved on recheck. Noting as its own cross-cutting item since a real user
  clicking the sidebar quickly could hit the same thing — worth a look, but NOT
  re-flagging individual lenses for this unless it doesn't resolve on reload.
- False "Session expired" / "Connection lost" / "Health: unreachable" error
  states (see `concord_qa_issues.md` finding #5) — assume this fires on
  every lens; only noting here if a lens shows something ADDITIONAL.
- 747-request over-fetch / 503s on new-account game-state endpoints — same,
  not re-logged per lens unless a lens surfaces a NEW distinct endpoint 503.
- **`chat` re-checked independently late in the walk (lens #260) and the original
  deploy-time finding reproduced again**: "Health: unreachable" + "Context: not
  loaded" + a "You don't have permission to do that" toast all fire simultaneously
  while 29 real DTUs and real threads render correctly underneath. Not a cold-start
  fluke — this is a standing defect on the platform's single most central surface.
- **`healthcare` is a genuine, reproducible 404** (lens #262), not a stuck-spinner
  or false-status issue like the rest of this list — `/lenses/healthcare` returns a
  raw, unstyled `Cannot GET /lenses/healthcare` (Express-shaped 404, not even a
  styled Next.js error page), reproduced twice identically. This is the ONE lens in
  the entire 266-lens walk that is not merely degraded but completely unreachable.
  Flagging this as the single highest-priority item in this whole document — it's
  also one of CLAUDE.md's named flagship-depth lenses (real WebRTC telehealth).

## Progress: 266 / 266 — WALK COMPLETE

**Pattern now well-confirmed** (15+ sightings): a large fraction of lenses show
persistent stuck loading spinners / "Loading..." text past 2.5s that never resolve
within the observation window. Given the earlier evo-asset findings (real 503s that
self-heal in 2-3s) and the pervasive false "Connection lost"/"Health: unreachable"
signals, this is very likely the SAME root cause (racy auth-refresh / backend cold
paths for fresh-account state) manifesting across dozens of lenses, not dozens of
independent bugs. Continuing to note per-lens for completeness but treating this as
one systemic fix target, not 15+ separate ones.

**Design notes added going forward** per owner request — flagging standout visual/UX
observations (good and bad) alongside functional status, not just pass/fail.

### Fix priority, ranked

**P0 — fix first (2 items, both isolated/high-blast-radius):**
1. **`healthcare` route is a bare 404** (`Cannot GET /lenses/healthcare`) — the only
   completely unreachable lens in the whole platform, and one of the named flagship
   real-depth lenses. Likely a build/routing config issue, not a data issue — check
   whether `concord-frontend/app/lenses/healthcare/page.tsx` exists in the deployed
   build output and whether anything upstream (nginx/Cloudflare rule, a colliding
   route) is intercepting the request before Next.js sees it.
2. **`chat` shows contradictory broken-permission status while working underneath**
   ("Health: unreachable" / "Context: not loaded" / "You don't have permission to do
   that" toast, all while 29 real DTUs and threads render correctly) — reproduced
   twice, independently, at different points in the session. This is the platform's
   single most central feature ("talk to AI") and it currently reads as broken to
   every new user even though the data path is fine.

**P1 — the systemic pattern (affects ~85 of the 90 ⚠️ rows):**
The overwhelming majority of ⚠️ findings are the SAME symptom recurring lens after
lens: a panel (or the whole page) gets stuck on a "Loading..."/"Connect to receive
real-time updates"/skeleton-placeholder state that never resolves within the
observation window, frequently paired with a "Disconnected" status pill even when
adjacent data (DTU counts, stat cards) is clearly real and rendering correctly. This
was seen on dozens of otherwise well-built, deeply-designed lenses (accounting,
mining, ml, move-builder, realestate, reasoning, science, services, sim, space,
telecommunications-adjacent lenses, and many more) — strongly suggesting ONE shared
root cause (a racy websocket/real-time-connection layer, or an auth-refresh
interceptor that's over-aggressive on first load) rather than 85 independent bugs.
**Fixing the shared connection/status layer is very likely the single highest-leverage
fix available** — it would silently resolve the majority of this document's ⚠️ rows
without touching each lens individually. See the "Cross-cutting issues" section at
the top of this file for the specific evidence trail (racy auth-refresh interceptor,
`[API] auth refresh failed, redirecting to login` firing ~15+ times per session).

**P2 — genuine near-blank renders (10 lenses, distinct from the stuck-spinner pattern):**
`metacognition`, `metalearning`, `move-builder`, `ops-telemetry`, `privacy`,
`reflection`, `security`, `fork` — these render essentially NO page chrome at all
(no nav tabs, no header, just a spinner filling the viewport), which is a worse
failure mode than the "chrome renders but body is stuck" pattern above and may
indicate a distinct bug (e.g., a data-fetch that's required before ANY chrome
mounts, vs. lenses where chrome and data are fetched independently). Worth
triaging as its own smaller cluster.

**P3 — needs re-verification, not a confirmed live bug:**
The original deploy-time finding of a permanently-black World Lens 3D viewport
(`THREE.WebGLRenderer: Context Lost` + `[ConcordiaScene] render frame failed`
looping every frame) did **not** reproduce on a later, independent visit to `/lenses/world`
during this walk — the scene rendered fully with a working HUD. The error strings
are still present in console history from the original deploy-time visit, but this
walk's tooling can't confirm whether the crash is now fixed, or is intermittent
(e.g., tied to a cold GPU-context state right after deploy). Recommend a targeted
re-test (repeated cold loads of `/lenses/world`) before deciding whether this is
closed.
