# ADR 011: `pg` (node-postgres) as a regular server dependency

| Field      | Value                                                  |
|------------|--------------------------------------------------------|
| Status     | Accepted                                               |
| Date       | 2026-09-27                                             |
| Authors    | Owner (commit 08fe77f0d); ADR recorded afterwards       |
| Supersedes | The earlier placement of `pg` in `optionalDependencies` |
| Scope      | server runtime dependency                              |

## Context

`server.js` has a PostgreSQL integration (`PG_CONFIG` / `initPostgres()` /
`runMigrations()`, the "Wave 9 database integrations" block): when
`POSTGRES_URL` or `DATABASE_URL` is set it opens a `pg.Pool` and keeps DTUs,
sessions, plugins, webhooks, automations, collab sessions and whiteboards
there. Without a connection the server reports `mode: "in-memory"` and runs on
its in-process stores.

`pg` sat in `optionalDependencies`. Under npm 11, an optional dependency that
the hidden lockfile had pruned was silently not installed, so from about
2026-09-09 every backend boot logged `Cannot find package 'pg'` and fell back
to the in-memory mode — even on boxes configured with a database URL. Nothing
failed loudly; data meant for Postgres simply wasn't going there.

Postgres is now the production data layer, so its driver is not optional.

## Decision

Declare **`pg`** in `dependencies` (pinned, currently `8.23.0`), and `redis` in
`dependencies` alongside it (Redis's role is covered by ADR 005). The
integration itself is unchanged: `pg` is still imported lazily inside
`initPostgres()`, and a box with no `POSTGRES_URL`/`DATABASE_URL` still runs
exactly as before — the package is present but never loaded.

## Why not the alternatives

- **Keep it optional:** that is what caused the silent fallback; an optional
  install that can quietly not happen is the wrong contract for the
  production database driver.
- **Another driver (postgres.js, Prisma, Knex):** `pg` is what the existing
  integration is written against; swapping the driver is a larger change with
  no benefit for this decision.
- **SQLite only:** SQLite (better-sqlite3) remains the in-process substrate for
  the macro/DTU engine and single-box installs; Postgres serves the multi-user
  production deployment.

## Consequences

- `npm ci` always installs `pg` (pure JS, no native build); install size grows
  slightly.
- Operators must still set `POSTGRES_URL`/`DATABASE_URL` for Postgres to be
  used; `/health` reports whether it is connected.
- The npm 11.6.2 lockfile bug that drops `pg` (see repo notes) no longer
  applies to a regular dependency, but lockfiles should still be regenerated
  with npm ≥ 11.20.
