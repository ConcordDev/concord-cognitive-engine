## 1. RESEARCH — the shape of the problem, from the code's own doctrine

The server's quest doctrine is written into `server/routes/worlds.js` at the old progress endpoint, which now **refuses** with HTTP 409: *"Progress is recorded by the server action itself; reach_location / interact / observe / deliver are reported through POST /api/worlds/:worldId/quests/:questId/report."* Two writer classes exist by design:

1. **Server-earned progress** — the server action that earns an objective calls `quest-engine.recordObjectiveProgress` itself (a generic matcher: exact `type` + `target` against the player's active quests).
2. **Client-reported progress** — for what the server cannot observe (reaching a place, interacting, observing), an **owner decision dated 2026-10-26** created `server/lib/quests/quest-report.js`: the client reports, and the server accepts only for an accepted, active quest, an objective that quest really has, in the player's live world, one unit per report, rate-limited (1.5 s); `deliver` is *not* taken on trust (the item must be held; one is consumed per unit). Server-earned types are refused on this channel so a client cannot skip them.

So the research question was never "write the writers" — it is: **which links of this designed chain are actually connected, and which objective types fall outside the design entirely?** The audit (§2) answers link by link.

## 2. AUDIT — the chain, link by link, on current origin/main

**Writers that exist (server-earned):** `kill` + `defeat` (worlds.js combat path, both spellings emitted), `gather` (worlds.js), `talk_to` (worlds.js NPC dialogue path), `cook` + `consume` (server.js world endpoints, incl. the `first_cycle_recipe` alias), `reach_location` (server.js `POST /api/world/reach-location`, a browser-frontend self-report endpoint).

**The client-report module is wired on three surfaces:** the `/unity-ws` gateway event **`quest:report`** (server.js dispatch; stamps the player's live-presence world; answers `quest:report:ack`), the REST twin `POST /api/worlds/:worldId/quests/:questId/report`, and the lens action `quests.reportObjective` (domains/quests.js).

**The gaps — five, each verified:**

- **G1 · No client ever sends the report (the big one).** Literal greps for `quest:report`, `ReportObjective`, `QuestReport`, `/report` across the Unity client's `Assets/` and the browser client's `src/` return **zero**. The full server chain (module → gateway event → ack) terminates in a sender that doesn't exist in either client. Every `interact` (17 objectives in top-level content), `deliver` (15), and `observe` (12) objective — and gateway-path `reach_location` (37) — is therefore un-recordable from gameplay today, however complete the server side is. *This reframes QUEST_AUDIT's headline: the writers were built (the report module's owner decision is dated the same day as the audit); the last hop was not.*
- **G2 · `talk_to_npc` spelling (confirmed).** The seeder's authored→System B mapper (`content-seeder.js: mapAuthoredObjectivesToSystemB`) passes objective `type` strings through **verbatim** — no normalization. Content carries `talk_to_npc` (7 objectives in top-level files; QUEST_AUDIT counts 10 across all sources) while every server talk path emits `talk_to`. Those rows can never match. One-line class of fix (normalize at seed), plus a reseed/backfill note for already-seeded rows.
- **G3 · `travel` (5) and `macro` (4) have no writer anywhere.** Both pass through the seeder verbatim; neither is server-earned, and neither is in `CLIENT_REPORTED_TYPES`. A quest containing one can never complete server-side. These are **vocabulary** gaps, not code accidents: `travel` wants a ruling (alias of reach_location? its own client-reported type?), `macro` wants a writer hung off lens-macro completion (a server action that exists — `lens:run` — so a server-earned writer is doctrinally clean).
- **G4 · `any_of` objectives are omitted at seed — deliberately, and correctly for now.** The mapper's own comment: seeding one row per branch would turn "any ONE of N" into "ALL N required" under `checkQuestCompletion`'s all-rows rule. The cost: server-side completion state for those quests diverges from the authored shape (the server can complete the quest without the branch objective). Proper support is an engine change (objective groups in the completion check) — real work, sized separately in §3, not a patch.
- **G5 · Canon quest sync is incomplete, and onboarding references a quest that doesn't exist.** Canon (`Assets/Concordia/Resources/Concordia/Canon/`) holds **32 quest files across 9 worlds**. Against `content/quests/`: **7 hub files are missing** (`consolidation-stake`, `faction-quests`, `first_cycle_phase_d`, `kael-torchlight`, `main-arc`, `southern-arc-mystery`, `the-handshake-revelation`) and **the sere world has no Canon folder at all** (its sub-world quests absent; QUEST_AUDIT's "8 files" counts sere's main-arc — reconciled in §5). Onboarding (present in Canon) names `cracks_in_the_compact` and `first_cycle_phase_d` as quests to load: the latter exists in content but not Canon (G5 proper), and **`cracks_in_the_compact` has no definition anywhere** — it is referenced by content's onboarding + main-arc and by Canon's onboarding, and defined in no file. Unity cannot load what doesn't exist; this needs an authoring ruling (write it, or remove the references), not a sync.

**Reconciliation with QUEST_AUDIT:** its *measurements* (135 quests / 314 objectives; Unity 250/97; server 83/3, 2026-10-26) stand as the last measured state — this dossier did not re-measure (no live DB from this seat). Its *cause* ("reach_location, interact, deliver, observe have no server writer") is **superseded** for those four types: the writers exist and are gateway-wired; the break is G1 (no sender) + G2/G3/G5 for the tail. Its talk_to_npc and Canon findings are **confirmed** and extended (G2 mechanism, G5 census).

**What it can do.** When W1–W3 land, the server's quest record becomes the true one for the first time: a player who walks to the glade, talks to the NPC, picks the herb, and delivers it sees **all four** objective kinds advance in the server's own state — quests complete server-side, rewards claim through `claimQuestRewards`, and the A-34 persistence work stops fighting a local-only shadow of quest state. The 83-vs-250 measurement becomes re-measurable, with a named method (QUEST_AUDIT's own audit tool) to prove the gap closed.
- **JUICE:** this is the payoff wiring. The moment a quest *completes* — the turn-in that lands, the reward that actually grants — is the loop's dopamine beat, and today it can only happen inside Unity's local state while the server shrugs. Wired, the completion is real everywhere at once: HUD, server record, and rewards agree, and the next quest the NPC offers you is offered *because the server knows you finished the last one* (world_quests close on completion in the engine — the giver can post again).
