## 1. RESEARCH — what securing the import actually requires

**The question.** The 110 Mixamo clips are Unity-imported in exactly one place — the `aura-wt` worktree on Ramaj's Mac — and are untracked there. What is the safest way to make that import durable, given how this repo actually stores binary assets?

**Evidence (all read first-hand):**

1. **The clips are not git-ignored; the characters' future home is.** `unity-client/.gitignore` ignores `Assets/Concordia/Models/**` ("Mixamo / character FBX (~587MB). Restore locally from the kitchen tree"). The clips live in `Assets/Concordia/Animations/Mixamo/`, which **no ignore rule covers** — they are simply uncommitted.
2. **The worktree's own branch doesn't hold them either.** aura-wt sits on branch `aura/gameplay` (its `.git` file and worktree HEAD read directly; the repo lives at `/Users/dutch/concord vs code/concord-cognitive-engine`). That branch **is** pushed to origin (head `60b7ab9f`, 2026-10-26) — and listing it shows **no `Assets/Concordia/Animations/` folder at all**. The import is untracked on every branch.
3. **All binary assets in this repo are Git LFS objects.** The repo-root `.gitattributes` (read in full, 28 lines) routes `*.fbx`, `*.glb`, `*.png`, `*.jpg`, `*.jpeg`, `*.zip`, `*.exr`, `*.obj`, `*.gltf`, `*.bin`, `*.ogg`, `*.aseprite`, `*.unityweb` through `filter=lfs`, plus 8 individually named HubKit/PolyHaven files. This is why tracked "sizes" for assets read as ~130 bytes — that is the LFS pointer, not the content.
4. **The repo's own config says the LFS budget is exhausted.** Above four exempted PWA icon paths, `.gitattributes` carries the comment: *"The Git LFS budget for this repo is exhausted, so these four stay in git"* — with per-path exemptions written as `!filter !diff !merge -text`. Whether the budget is *still* exhausted today is **not verified** (GitHub-side state; visible to Ramaj, not to this lane).
5. **Size is not the obstacle; the storage route is.** The import totals **65.0 MiB** of FBX (largest single clip 1.8 MB) — small next to files the repo already carries as plain git blobs (largest observed under unity-client: a 6.7 MB GIF, a 4.8 MB GIF, a 1.4 MB PDF; GIF/PDF are not LFS-routed). Per-file, these FBX are unremarkable. The decision is purely *which storage rail* they ride.

**Options, with trade-offs:**

| Option | Mechanism | For | Against |
|---|---|---|---|
| **A — Commit via LFS** (repo default) | Add the folder; `.gitattributes` routes the FBX to LFS automatically | Canonical; matches every other FBX in the repo; clones stay light | Pushes 65 MiB against a budget the repo's own config calls exhausted (state today unverified — Ramaj-visible only); if the budget is dry, the push fails or bills |
| **B — Exempt + plain-git commit** | Add exemption lines for the Mixamo path to `.gitattributes` (same `!filter !diff !merge` pattern as the PWA icons), commit 65 MiB as ordinary blobs | Works regardless of LFS budget; precedent exists in the same file, for the same stated reason; one-time cost | +65 MiB permanent weight in every full clone, forever |
| **C — Archive-only** | Zip the imported folder (with `.meta` files) to verified off-repo storage; git stays untouched | No repo change at all | Weakest: restore stays manual, the "kitchen tree" pattern that already failed once; the import remains effectively single-copy for working purposes |
| **D — Split (recommended shape)** | Clips via **B** (or A if Ramaj confirms LFS headroom); the ~1.05 GiB of `Models/**` native content (see §5) decided **separately**, archive-first | Matches each asset class to its scale: 65 MiB is hygiene, 1.05 GiB is a budget decision | Two decisions instead of one |

**Recommendation:** Option D, with B as the clips rail unless Ramaj confirms the LFS budget has headroom (then A is equally good). The dossier's plan (§3) is written to work under either A or B — only one sub-step differs.
