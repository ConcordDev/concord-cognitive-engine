## 0. Verdict (read this first)

The Concord **kernel is already alive**. NPC routines, faction strategy, seasons, economy, fauna, `city-presence.applyAttack` all tick on the server.

What is **not** alive is any native client presenting that kernel in the browser:

| Tree | What it is today |
|---|---|
| **Server** | Kernel. Real. |
| **Three.js world-lens** | OS HUD (DTUs, presence, stations). Combat *can* hit the kernel. `currentWorldId` is pinned to `concordia-hub`. Not the AAA presenter. |
| **Unity Editor** | Offline procedural hub. Combat ack only if `/unity-ws` connects. **Travel, NPC brains, HP, persist, `player:move` are local.** `SendMove` is dead code. |
| **Vite `src/game/`** | Richest “feels alive” loop. **Zero network.** localStorage persist. Explicitly superseded. Do not ship it into the frontend. |
| **Godot** | Parity native client. **Web export pipeline already exists** (`npm run export:web` → `/godot-client/`). **No world-lens iframe yet.** |

**Unity WebGL export ran on this Mac 2026-09-03** (`npm run export:unity-web` exit 0). The player is committed so CI clones and the live site load Unity, not Three.js. Three.js stays the honest fallback only when those files are deleted.

**The website already knows how to serve a WASM 3D client** (Godot). Unity clones that path, with one difference: Godot's ~42MB wasm stays gitignored; Unity's ~17MB ship **is** in git so a deploy box without the Editor still presents Concordia.

## 2. Native Unity audit (WebGL blockers)

Unity **6000.5.9f1** is on this Mac (`/Applications/Unity/Hub/Editor/6000.5.9f1`). Project: `apps/concordia-living-world/unity-client/`.

### P0 — will not play in a browser

1. **`System.Net.WebSockets.ClientWebSocket`** (`Assets/Concordia/Scripts/ConcordClient.cs`) — IL2CPP WebGL has no working stack. Must be browser `WebSocket` via `.jslib`.
2. **`FreePacks` is Editor-only** (`AssetDatabase.FindAssets`). Player/WebGL `Mesh()` always returns null → cubes / missing world.
3. **No scene in git.** `EditorBuildSettings` points at `Assets/Scenes/ConcordiaHub.unity`, which is generated by `Concordia/Build Hub Scene` and never committed.
4. **URP pipeline GUID** in `GraphicsSettings` has no matching asset in the repo (magenta until `ConcordiaUrpEnsure` runs in Editor).
5. **Kenney / Mixamo / Get Started packs are not in git** (`Models/**` gitignored ~587MB). Kitchen looks like Concordia only on the machine that imported them.

### P1 — wrong but survivable

- `File.WriteAllText("/tmp/...")` in `ConcordiaGame`, `ModularPerson`, `ConcordiaShot` (try/catch; `ConcordiaShot.Grab()` still runs every Start).
- `DestroyImmediate` in play mode (`WorldBuilder`).
- Pointer lock assumes desktop; WebGL needs a click-to-capture gesture.
- `webGLThreadsSupport: 0` (correct — we will not turn on COOP/COEP).
- `player:move` / `combat:dodge` APIs exist and are **never called**.
- `scene:data` is requested and **ignored**; `WorldBuilder` stays local.
- `Travel()` is a local enum swap — **authority violation**.
- `Hostile.TakeHit` damages local player HP — **authority violation**.
- Training dummy `targetId` is the GameObject **name**, not a kernel NPC id.

### What Unity already does right

- Procedural hub boot (`ConcordiaGame.Start`) does not need a baked open world.
- Combat, when connected, is intent → `combat:attack:ack` (PR #953).
- Offline path is honest `{ok:false, reason:'no_gateway'}`.
- Editor scripts (`ConcordiaBoot`, MCP, Asset Store pull) do not ship in player.
- Input falls back to legacy Input Manager (`activeInputHandler: 0`) — WebGL-ok.

### Vite prototype (do not embed)

`apps/concordia-living-world/src/game/{combat,npc-life,persist,kernel,sim,evo}.ts` — complete local sim, **zero** `fetch`/WebSocket. `concord-frontend` imports none of it. Keep as spec.

## 3. Website / deploy audit (already built for Godot)

Proven by reading `scripts/export-godot-web.mjs` + `app/godot-client/index.html/route.ts` + a **real browser CSP failure** documented in that file:

| Piece | Godot | Unity (target) |
|---|---|---|
| Export script | `npm run export:web` | `npm run export:unity-web` |
| Static bytes | `public/godot-client/*` (gitignored) | `public/unity-client/*` (**committed**, ~17MB) |
| `index.html` | **Not** in public/; nonce-injected route | same; committed copy at `public/unity-client/export-index.html` |
| Honest 404 | `godot_web_export_not_built` | `unity_web_export_not_built` |
| Middleware public prefix | `/godot-client/` | `/unity-client/` |
| CSP | `wasm-unsafe-eval`, `worker-src blob:`, `frame-src 'self'` | already sufficient |
| Threads / COOP+COEP | off | keep off |
| `public/` in standalone | `startup.sh` + Dockerfile copy | same |
| **World-lens iframe** | **none** (explicitly out of scope in export script) | **this plan** |
| WS through tunnel | `/godot-ws` → :5050 | `/unity-ws` in cloudflared + nginx |

**Load-bearing deploy fact:** Next rewrites do **not** forward WebSocket upgrades. In-page Unity must connect to `wss://<site>/unity-ws` which **must** hit the backend (:5050), same as `/godot-ws` / `/socket.io`.
