**Lessons from this pass, worth carrying into future doc-order walks:**
- Before assuming a "blocked, needs X" note in an audit doc is still true, grep the CURRENT tree for the macro/test first (`grep -rl "<keyword>" server/domains server/tests`) and re-read the actual call chain rather than trusting the doc's premise. Five items in this pass (`law`, `landscaping`, `creatures`, `finance`, `defense`) turned out to have stale "still needed" premises — the real gap was smaller, different, or already closed by an earlier/concurrent session. Re-deriving from scratch before that check wastes effort a two-second grep would have shortcut.
- Checking the actual data path (not just "does it render") surfaced real, previously-undiscovered bugs at a high hit rate: a broken pre-existing test mock (#10 `logistics`), a phantom-success field-read bug that silently zeroed out a real feature (#12 `landscaping`). Reading the real code instead of trusting a stale doc note pays for itself beyond just closing the doc item.
- A design-taxonomy decision (the 4 accent-color items) is categorically different from a "read real data, build the view" item — it has no objectively-correct answer to discover in the code, so it's worth explicitly flagging for the owner's input rather than picking unilaterally, even under time pressure to close out a backlog. Once given direction ("make it appealing, close it out"), the actual implementation was still small and mechanical.
- Installing new npm dependencies for a small, contained feature (`global`'s choropleth) can surface unrelated, real, pre-existing repo-wide problems (the `typescript`/`typescript-eslint` version conflict) that are out of scope to fix in the same pass — flag clearly, don't let it block the actual task, and don't attempt a unilateral fix on a decision that affects the whole repo's tooling.

## Session discipline reminder (carried over from the parent walk)

- Every visualization must be built from REAL backend data traced end-to-end (grep the actual macro/route, read its real return shape) — never fabricate a data model to make a diagram look good. Every one of the 9 done items above followed this; several required extending a real backend function additively (e.g. `computeCascadeTree`) rather than inventing new data.
- Typecheck (`npx tsc --noEmit -p .` in `concord-frontend/`) + lint (`npx eslint <file>`) + run whatever existing test file covers the touched lens, every time, before considering an item done.
- Writing a NEW pinning test for genuinely new logic (not just UI wiring) is worth it — it caught a real bug in the IPA affricate segmentation (#5) that would otherwise have shipped broken.
- If you find a pre-existing, unrelated test failure while verifying (like `household`'s `ChoreBoard.tsx` — see #7), confirm via `git diff` that you didn't cause it, flag it honestly in both this doc and the `LENS_DESIGN_UPGRADE_PLAN.md` entry, and move on — don't silently ignore it, and don't burn the session fixing something unrelated to the current task (per CLAUDE.md's "pre-existing is an explanation, never an excuse" — reclassify as debt, name it, don't own it if it's not yours to fix right now).
